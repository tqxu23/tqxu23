## Background: RISC-V Vector Extension（RVV扩展）

在RISC-V架构中，RISC-V Vector Extension（RVV扩展）专门用于优化那些**数据并行性强、具有大量重复性运算的工作负载**。例如，图像处理、机器学习、科学计算（如矩阵乘法、向量加法）、加密解密算法以及信号处理等，这些任务通常涉及对大规模数据集的批量运算。


::mention-block
### 🤔 CPU核设计中RVV扩展的位置

总体上，我用下图简单地描述在CPU核中使用RVV（和其他指令集中向量扩展）的主要场景之一，它希望通过向量指令更好地支持部分灵活的小规模专用加速。CPU上的RVV扩展不是为了替代GPU、Accelerator等并行硬件而存在的，它的并行度低于专用硬件，但灵活性、普适性却高很多。

RVV 作为可选指令支持，在愿景上期望在开启后获得性能增强。然而事与愿违，**开启向量化的部分程序上非但没有出现性能提升，反而出现了大量的性能下降**。下图展现了在KMHV2上进行测试的结果。结论上，除了HMMER外，SPEC06INT的其他项都出现了不同大小的性能下降。

::markdown-note

**性能无法上升是情理之中的。** 在共识上，SPEC06的很多负载实际上不适合进行向量化。例如图中下降最明显的omnetpp，其负载是通信网络系统模拟，本身的不规则控制流就难以通过支持RVV实现性能提升。然而，**性能下降或许是意料之外的。**不应因为开启了向量化，我们的性能反而出现了下降。这是不符合指令扩展的理念的。

**我们对向量化的“负优化”行为感到疑惑，我们希望自顶向下地查明具体负优化的来源在哪里。这是现阶段进行向量化探索的初衷。**

::mention-block
### 🤔 什么是“自顶向下”？

性能探索非常复杂，因此我们希望在性能探索中使用 **第一性原理** 来定位问题，也就是说，我们从最基本、最本质的不可再分的原理出发去思考，而不是依赖经验、惯例或类比。

为什么会出现负优化呢？考虑到程序流（或者汇编代码的指令流）都在根据程序员编写的代码做相同的事，那么 **我们理论上一定能够找到一部分代码，开启向量化之后运行速度变慢了。** 而且只要我们把这段变慢的代码变快（作为lower bound，甚至手动地关闭向量选项），它就能够变快，从而使得整个程序变快。

为什么说这是自顶向下的呢？因为我们没有直接去追溯ISA和微架构的问题，而是从Application性能出发，**把软件源代码作为靶点先找原因，再去向下去看ISA和微架构的问题**。

![自顶向下的性能优化](images/250818-Topdown-RVV/topdown-arch.png)
::markdown-note
自顶向下的性能优化
::

**与之相对应地，自底向上是另一个很重要的提升性能的方式。** 先从底层出发，通过对比SOTA实现、不断地优化V扩展指令的微架构，使得其中某些V扩展指令变得更快，进而使得软件负载变得更快。可以说，这两种方法是相辅相成的。
::

## Challenge1: 性能差异从何而来？

与其他针对微架构的硬件性能探索不同，针对指令集进行性能解释是一个技术栈跨度较大的问题。这使得性能现场的定位都变得比较困难。**根本原因是我们使用现有方法很难对编译器生成的不同指令流做对比。**

下图展现了RVV探索的主要挑战。在获得性能结果后，我们实际上无法真正地定位到性能现场，因为在经过编译器的不同编译过程后，程序流已经发生了变化。在其他的微架构探索中，我们可以在微观上逐指令对比延迟（例如指令间commit的延迟）和计数器来进行性能解释。在RVV探索中这已无法奏效。

性能现场定位是我们想到的另一条路径。它本质上是一种profiling方法，我们期望先反向找到在开启RVV后性能变化最大的代码段（**性能现场**），再去通过比较指令流等方式进行**性能解释**。

### 🤔 我们在其他问题上是怎么做性能探索的？
通常情况下，进行微架构性能探索的工作流可能像这样：

① 我们想到了一个新的关于微架构设计的想法，这可能来源于 论文实现/负载分析/模型调优 ......

② 我们想在cmodel上先验证一下这个想法是不是真的有用。我们会使用已有的SPEC负载（用simpoint切片）进行测试比较，跑分后看看分数有没有上升

③ 我们得验证这个分数收益真的是我们所想的那样，修改的微架构真的发挥了作用。这时候我们需要借助topdown / 增加性能计数器 等一些方式解释我们的性能变化的原因

如上所示，**我们通常是针对同一个负载进行的比较，这在RVV上是不易实践的。**

## Challenge2: 性能现场如何定位？
进行性能现场的定位本身也是比较困难的。虽然在基于cmodel/rtl进行性能仿真时，我们能够通过性能计数器等获得所有的性能信息，但是这些信息无比地琐碎，它们通常无法直观地提供有价值可比较的性能现场定位，更没有明晰这些执行中的指令到底在做什么，以及它在软件上是哪一块的逻辑。

因此，我们即使能够通过指令性能追踪的方式获得各个执行指令的性能，也很难将RVV指令流定位和对比。下图具体地表现了我们遇到的两个困境：

+ 在横向上，向量化的函数可能被内联和展开，我们不知道这些v扩展指令源于什么代码，使得定位困难。
+ 在纵向上，由于我们考虑仿真时间，通常需要通过simpoint方法进行切片再跑分，这使得不同指令流可能完全获得不同的切片结果，使得scalar和vector间比较困难。

![性能现场的定位困境](images/250818-Topdown-RVV/performance-test-challenge.png)
::markdown-note
性能现场的定位困境
::

甚至，这并非只是向量化探索才会遇到的问题。对于任何指令扩展和跨指令扩展的对比，甚至对于其他异构计算的场景，这都是在性能探索中可能遇到的共性问题。

## Methodology1：Instruction-level Analysis

**在很多情况下，我们实际上通过对编译后的指令进行分析就能有一些结论。**

### STEP1：保留调试信息，重新编译负载

我们需要重新从源码级构建负载，重新构建的目的在于需要保留debug信息。在gcc中，只需要增加参数-g即可。

### STEP2：直接使用用户态程序，并在行为模拟器（QEMU）上直接统计性能结果

使用QEMU的Plugin的功能，可以很好地对指令进行统计。最经常使用的Plugin是统计负载的Basic Block或各个指令类型的数量。

QEMU的官方页面：[https://www.qemu.org/](https://www.qemu.org/)

QEMU的Plugin功能可以从这个教程开始：[QEMU TCG Plugins详解](https://blog.csdn.net/JaCenz/article/details/125302647)

这个方式有时可以让我们直接定位那些向量化支持不完备负载的性能问题。例如，在统计xalancbmk和omnetpp这类向量化后性能下降的负载后，我们通过简单地对这两个负载的向量化指令位置进行统计，就发现了它strlen和strcmp上可能存在向量化反向优化的情况。

## Methodology2：Profiling-based Performance Tracing

**对于那些复杂负载，我们主要以source code作为靶点，做软硬件的协同性能追溯。**

我们需要同时考虑编译器和硬件的性能差异，并在此基础上做源码级的比较。

### STEP1：正向性能测试

同样地，我们需要重新从源码级构建负载，重新构建的目的在于需要保留debug信息。在gcc中，只需要增加参数-g即可。我们也同时需要准备unstripped的kernel binary，这其中保留了各个指令对应的源码/源函数名。在构建负载后，使用已有工具打checkpoint、再基于perfcct工具用GEM5进行性能测试获得，各个指令的延迟信息。

![正向性能测试](images/250818-Topdown-RVV/performance-test.png)
::markdown-note

### STEP2：反向性能追溯

由于我们已经获得了各个指令的延迟信息，又可以反向地通过addr2line工具获得各个指令对应的源码位置（因为我们保留了debug信息），因此我们理论上就可以像下图的“src-level perf”中表现的那样，获得每行代码的延迟信息了。通过比较，我们可以了解到某行/某段代码的性能差异大，也就可以再围绕差异段落进行性能解释了。
